# Catering Booking System REST API — Full Implementation Review

This is a Spring Boot 3 / Java 21 REST API implementing a catering booking system with role-based access (ADMIN/USER), booking lifecycle management, a cancellation refund matrix, deposit/full-payment flows, and three invoice types. The implementation covers all four feature milestones (FEAT-001 through FEAT-004) and the overall shape is correct. The main concerns centre on a misread of the cancellation boundary condition, an unhandled exception type that leaks user-existence information, and a plain-text OTP in the database.

**Watch for:**
- **confirmed** — The cancellation boundary uses `> 3` / `<= 3` but the spec says `> 4 days` / `<= 3 days`. On day-4 exactly, the code refunds; the spec says day-4 is the non-refundable threshold.
- **confirmed** — `UsernameNotFoundException` extends `AuthenticationException`, not `RuntimeException`, so it bypasses the `IllegalArgumentException` handler and falls into the generic 500 catch-all. Callers hitting `/forgot-password` or `/verify-otp` for a non-existent email get a 500 instead of a 404.
- **confirmed** — The OTP is stored plain-text in the `resetOtpCode` column. A DB read (or a compromised backup) exposes a live credential.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The JWT layer uses JJWT 0.12.x correctly throughout — `Keys.hmacShaKeyFor`, `Jwts.parser().verifyWith(...).build().parseSignedClaims(...)` — and the circular-dependency between `SecurityConfig`, `UserService`, and `PasswordEncoder` is resolved by isolating `PasswordEncoder` in a separate `AppConfig`. The filter chain, stateless session, and public/admin endpoint rules are wired as specified. The password validator enforces all five character-class rules and the case-insensitive name/surname check. OTP expiry is 2 minutes, enforced at verification time. The OTP is stored plain-text in the database — a compromised backup exposes a live reset credential.

The 5-day advance booking rule is `daysUntilEvent < 5`, which correctly rejects anything with fewer than 5 full days. The 3-booking cap counts only `PENDING` and `CONFIRMED` statuses. Transport cost applies `(distanceKm - 15) * 25` only when `distanceKm > 15`, matching the spec.

The cancellation matrix has a boundary bug: the spec draws the line at **4 days** (cancelling with > 4 days remaining gives a full refund; ≤ 3 days forfeits the deposit). The code uses `> 3` / `<= 3`, which misidentifies the boundary. A cancellation exactly 4 days before the event should forfeit the deposit; the code currently refunds it.

The `InvoiceController` endpoints — `GET /api/invoices/booking/{bookingId}` and `GET /api/invoices/{invoiceId}` — are accessible to any authenticated user. There is no ownership check: user A can retrieve invoices for user B's booking by guessing the booking or invoice ID.

`UsernameNotFoundException` is thrown from `initiatePasswordReset`, `resetPassword`, and `verifyOtp` in response to unknown emails. It extends Spring Security's `AuthenticationException`, which the `GlobalExceptionHandler` doesn't register an `@ExceptionHandler` for, so it falls through to the generic 500 handler. The correct response here is 404 (or, to avoid user-enumeration, a 200 with a neutral message at the controller level).

<summary>Issues (6)</summary>

1. **Cancellation boundary off-by-one** — The spec table header reads "> 4 days" / "≤ 3 days"; the code uses `daysToEvent > 3` / `daysToEvent <= 3`. At exactly 4 days remaining the code issues a full refund, but the spec forfeits the deposit. Change all five branches in `BookingService.cancelBooking` from `> 3` / `<= 3` to `> 4` / `<= 4`.

2. **UsernameNotFoundException → 500** — `GlobalExceptionHandler` has no handler for `UsernameNotFoundException` (or its parent `AuthenticationException`). Calls to `/api/auth/forgot-password`, `/api/auth/verify-otp`, and `/api/auth/reset-password` for an unknown email return HTTP 500 instead of 404. Add `@ExceptionHandler(UsernameNotFoundException.class)` returning 404 (or return 200 to avoid user enumeration — pick a policy and be consistent).

3. **Plain-text OTP in database** — `resetOtpCode` stores the OTP as-is. A DB read, backup leak, or audit log exposes an active reset credential. Hash the OTP with SHA-256 (or BCrypt) before persisting, and compare the hash on verification. The 2-minute window is short but a stolen DB dump can replay it within that window.

4. **Invoice ownership not enforced** — `InvoiceController.getInvoicesForBooking(bookingId)` and `getInvoice(invoiceId)` do not verify that the calling user owns the booking. Any authenticated user can enumerate invoices for arbitrary booking IDs. Pass `authentication.getName()` to the service layer and check ownership there, the same way `BookingService` and `PaymentService` do.

5. **`getPaymentForBooking` admin access gap** — `PaymentService.getPaymentForBooking` rejects anyone whose email doesn't match the booking's user, including admins. Unlike `BookingService.cancelBooking` and `getBooking`, there is no `isAdmin` bypass. An admin calling `GET /api/payments/booking/{id}` for any booking they don't personally own gets a 409.

6. **`UsernameNotFoundException` on the `/forgot-password` path leaks user existence** — Even if the HTTP status is changed to 404, returning a distinct error for unknown email vs. known email enables user enumeration. The controller should return 200 unconditionally and the service should silently do nothing for unknown emails — a common security pattern for password-reset flows.

## Cancellation boundary: spec says 4 days, code says 3

The original requirements state: "user cannot cancel if date of event is nearby 4 days" and the refund table header uses "> 4 days" / "≤ 3 days". The intent is that the non-refundable window begins when there are **3 or fewer** days remaining, making the boundary day **4**. A cancellation with exactly 4 days remaining falls into the forfeiture window under the spec, but the code's `daysToEvent > 3` treats 4 days as safe and issues a full refund.

The matrix check in `BookingService.cancelBooking` (confirmed, lines 176–190):

```java
if (daysToEvent > 3 && !payment.isDepositPaid() && !payment.isFullyPaid()) { ... }
else if (daysToEvent > 3 && payment.isDepositPaid() && !payment.isFullyPaid()) {
    refund = payment.getDepositAmount();          // <— wrong at daysToEvent == 4
```

Should be:

```java
if (daysToEvent > 4 && ...) { ... }
else if (daysToEvent > 4 && payment.isDepositPaid() && !payment.isFullyPaid()) {
    refund = payment.getDepositAmount();
```

All five branches need the threshold updated from 3 to 4.

## OTP plain-text storage

`UserService.initiatePasswordReset` stores the raw 6-digit OTP in `user.resetOtpCode` and the comment explicitly notes: "we just compare plaintext — no hashing for OTP". The `resetPassword` and `verifyOtp` methods then do a direct string equality check. A 6-digit OTP has 1,000,000 possible values — weak by brute-force standards — and storing it plain-text means any SELECT on the `users` table while a reset is in flight exposes the credential. The 2-minute window shortens the attack but doesn't eliminate it for bulk-query attacks against a compromised replica.

## Invoice access control gap

`InvoiceController` passes only the `bookingId` or `invoiceId` to `InvoiceService`. The service fetches the invoice from the repository with no ownership check:

```java
// InvoiceService.getInvoice — no caller validation
Invoice invoice = invoiceRepository.findById(invoiceId)
    .orElseThrow(() -> new EntityNotFoundException(...));
return toResponse(invoice);
```

Both `BookingService` and `PaymentService` do this correctly:

```java
if (!booking.getUser().getEmail().equals(userEmail) && !isAdmin) {
    throw new BookingNotAllowedException("You are not authorised ...");
}
```

The same pattern needs to be applied in `InvoiceService`, or the controller needs to verify ownership before forwarding the call.

## Admin bypass missing in PaymentService

`PaymentService.getPaymentForBooking` hard-checks ownership:

```java
if (!booking.getUser().getEmail().equals(userEmail)) {
    throw new BookingNotAllowedException("You are not authorised to view this payment");
}
```

No admin bypass. This is inconsistent with `BookingService.cancelBooking` and `getBooking`, which both check `currentUser.getRole() == Role.ADMIN`. An admin user calling `GET /api/payments/booking/{id}` for a booking they didn't create gets a 409 Conflict.

## `UsernameNotFoundException` falls to 500

Spring Security's `UsernameNotFoundException` extends `AuthenticationException` which extends `RuntimeException`. `GlobalExceptionHandler` registers handlers for `IllegalArgumentException`, `EntityNotFoundException`, `BookingNotAllowedException`, `CancellationNotAllowedException`, `MethodArgumentNotValidException`, `AccessDeniedException`, and the generic `Exception`. There is no handler for `AuthenticationException` or its subtypes. When `UserService.initiatePasswordReset`, `resetPassword`, or `verifyOtp` is called with an unknown email, the `UsernameNotFoundException` propagates up, skips all the specific handlers, and hits the generic `Exception` handler, which returns 500.

## Test coverage

There are no test files in the project. None of the business rules — the 5-day booking rule, the 3-booking cap, the cancellation matrix, transport cost calculation, or password validation — are covered by automated tests. Given that the cancellation matrix has an off-by-one error that would have been caught by a parameterised test against each matrix row, the absence of tests is a meaningful risk. At minimum, `BookingService`, `PasswordValidatorService`, and the refund matrix branches in `BookingService.cancelBooking` should have unit tests.
