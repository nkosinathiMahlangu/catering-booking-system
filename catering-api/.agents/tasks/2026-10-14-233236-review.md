# Catering Booking System REST API — Full Implementation Review

This review covers the complete Spring Boot REST API for the catering booking system, comprising auth (JWT, OTP, password reset), booking creation and cancellation with the refund matrix, deposit/full-payment processing with invoice generation, and catering package management. The implementation maps closely to the acceptance criteria across all four FEATs. The primary concern before shipping is a refund matrix boundary mismatch between the spec and the code that misclassifies the exactly-4-days-out case.

**Watch for:**
- **Confirmed** — Cancellation refund matrix uses `daysToEvent > 4` / `daysToEvent <= 4` everywhere, but the spec header rows are "> 4 days" and "≤ 3 days". At exactly 4 days the spec table is silent, yet the user requirement says "cannot cancel if date of event is nearby 4 days" — making 4 days the intent boundary. The code's `<= 4` correctly catches 4 days as non-refundable, but the inline doc and messages say "within 4 days" (which a customer reads as < 4). The boundary needs one source of truth.
- **Confirmed** — `User.java` Javadoc says "Plain-text OTP stored temporarily" but `UserService` stores a SHA-256 hash. Misleading comment, not a bug, but will confuse maintainers.
- **Confirmed** — No unit or integration tests beyond the empty Spring context loader. All business rules (refund matrix, transport cost, password validator, 5-day rule, 3-booking cap) are untested.
- **Likely** — `@Future` on `BookingRequest.eventDate` rejects today's date before the 5-day service check runs, but it also rejects *tomorrow* with a generic validation message. A customer submitting 2 days out gets a cryptic "must be a future date" instead of "must be at least 5 days from today." Ordering concern, not a breakage.

**Verdict**: NEEDS_CHANGES

---

## High-level view

Auth is solid end-to-end. JJWT 0.12.x API is used correctly (`Jwts.parser().verifyWith(...).build().parseSignedClaims(...)`), the `PasswordEncoder` bean lives in `AppConfig` not `SecurityConfig` so the circular-dependency trap is avoided, and OTPs are SHA-256 hashed before storage. The 2-minute expiry is set with `LocalDateTime.now().plusMinutes(2)` and checked correctly in both `UserService` and `AuthService`.

The booking creation rules are all implemented correctly — the 5-day advance check uses `ChronoUnit.DAYS.between(LocalDate.now(), eventDate) >= 5`, the 3-booking cap queries `countByEventDateAndStatusIn(date, [PENDING, CONFIRMED])`, and transport cost is `(distanceKm - 15) * 25` only when `distanceKm > 15`. The cancellation refund matrix is structurally correct for all scenarios, but the boundary constant (`> 4` vs `> 3`) does not match the spec's column headers and needs alignment.

Payment processing covers both flows. Deposit-only (`payFull=false`) marks `depositPaid`, sets `balanceDue = totalAmount - depositAmount`, sets status to CONFIRMED, and triggers Invoice 1. Full payment sets both paid flags, zeros `balanceDue`, and triggers Invoice 2. Invoice numbering is `INV-{year}-{05d}` implemented via a save-then-update pattern inside `@Transactional` methods.

Security configuration is correct for a stateless JWT API. Public paths (`POST /api/auth/**`, `GET /api/packages`, `GET /api/packages/{id}`) are permitted without auth; package mutations require `ROLE_ADMIN`; everything else under `/api/**` requires authentication. `@EnableMethodSecurity` is present and `@PreAuthorize("hasRole('ADMIN')")` guards the admin-only controller endpoints.

Error handling covers all required exception types with correct HTTP status codes. The only gap is that `BadCredentialsException` (thrown by `AuthenticationManager` on bad login credentials) falls through to the catch-all `Exception` handler and returns 500 instead of 401.

There are no unit or integration tests for any business logic. The only test file is an empty Spring context loader.

<details>
<summary>Issues (5)</summary>

1. **Refund matrix boundary ambiguity** — The spec matrix says "> 4 days" (refundable) and "≤ 3 days" (non-refundable), leaving exactly 4 days undefined. The code resolves this with `> 4` / `<= 4` (so 4 days = forfeited), which matches the user's "nearby 4 days" wording but contradicts the spec's column headers and the inline messages that say "within 4 days." Pick one explicit boundary (3 days or 4 days), document it, and make all messages consistent.

2. **`BadCredentialsException` falls through to 500** — Spring Security throws `BadCredentialsException` (a subclass of `AuthenticationException`) when the login password is wrong. `GlobalExceptionHandler` has no handler for this type, so it falls to the catch-all and returns 500. Add `@ExceptionHandler(BadCredentialsException.class)` returning 401 Unauthorized.

3. **`@Future` validation fires before the 5-day service check** — `BookingRequest.eventDate` is annotated `@Future`, which rejects dates from tomorrow onward with "must be a future date." A customer who submits 3 days out gets a generic validation error, never seeing the intended "must be at least 5 days from today" message. Replace `@Future` with `@FutureOrPresent` (or no constraint) and let the service's 5-day check produce the correct message, or swap to a custom `@AtLeastFiveDaysAhead` validator.

4. **`User.java` Javadoc says OTP is plain-text** — The `resetOtpCode` field comment reads "Plain-text OTP stored temporarily during a password-reset flow" but the stored value is a SHA-256 hex digest. Update the comment to "SHA-256 hash of the OTP" to prevent a future developer from comparing the submitted code directly against the stored value.

5. **No business-logic tests** — Every core rule (refund matrix, transport threshold, 5-day booking rule, 3-booking cap, password validator's name/surname check) is entirely untested. At minimum, unit tests for `PasswordValidatorService`, `BookingService.cancelBooking`, and `BookingService.createBooking` should be added before this goes to production.

### Refund matrix boundary: `> 4` vs `> 3`

The spec table has two rows with headers "> 4 days" (refundable) and "≤ 3 days" (non-refundable). There is no row for exactly 4 days. The user requirement says "user cannot cancel if date of event is nearby 4 days" — which reads as the cut-off is 4 days. The code implements `daysToEvent > 4` for the refundable side and `daysToEvent <= 4` for the non-refundable side, so at exactly 4 days the deposit is forfeited. This is probably the intended behavior, but the spec's "> 4" vs "≤ 3" wording creates a gap that makes it ambiguous, and the inline messages ("Cancellation within 4 days") are inconsistent with the "> 4 days" header in the spec table.

The actual matrix logic across all five branches is otherwise correct:

```
daysToEvent > 4, no payment made     → throw (nothing to cancel)
daysToEvent > 4, deposit only        → refund = depositAmount         ✓
daysToEvent > 4, fully paid          → refund = totalAmount            ✓
daysToEvent <= 4, deposit only       → refund = ZERO                   ✓
daysToEvent <= 4, fully paid         → refund = totalAmount - deposit   ✓
```

The else branch (no payment, `<= 4` days) allows cancellation with zero refund to free the booking slot — a reasonable extension of the spec not explicitly covered by the matrix.

### `BadCredentialsException` → 500

`AuthService.login` delegates to `authenticationManager.authenticate(...)`, which throws `BadCredentialsException` on wrong password. `GlobalExceptionHandler` handles `IllegalArgumentException`, `EntityNotFoundException`, `UsernameNotFoundException`, `AccessDeniedException`, and the two domain exceptions, but not `BadCredentialsException` or its parent `AuthenticationException`. The catch-all `Exception` handler returns 500 with "An unexpected error occurred." A bad login returns 500, not 401. Fix:

```java
@ExceptionHandler(BadCredentialsException.class)
public ResponseEntity<Map<String, String>> handleBadCredentials(BadCredentialsException ex) {
    return buildError(HttpStatus.UNAUTHORIZED, "Invalid email or password.");
}
```

### `@Future` validates before the 5-day service gate

`BookingRequest.eventDate` carries `@NotNull @Future`. Bean validation runs before the controller hands off to `BookingService`, so a date that is tomorrow fails at validation with "must be a future date." The intended behavior — a clear "Event date must be at least 5 days from today" message from the service — is never reached for dates that are future but within 4 days. Removing `@Future` and relying solely on the service check fixes this, or a custom constraint can encode the 5-day rule at the DTO layer directly.

### OTP storage: misleading Javadoc on `User.resetOtpCode`

`UserService.initiatePasswordReset` calls `hashOtp(otp)` and stores the result. The `hashOtp` method computes a hex-encoded SHA-256 digest. The `User` entity's field-level Javadoc says "Plain-text OTP stored temporarily." Anyone reading the entity to understand the reset flow would conclude the raw code is in the database. Correcting the Javadoc is a one-line fix with real maintenance value.

### Test coverage gap

The test directory contains only `CateringApplicationTests` with an empty `contextLoads()` test. None of the following are tested:

- `PasswordValidatorService`: name/surname containment check, each of the five rule failures
- `BookingService.createBooking`: 5-day rule, 3-booking cap, transport cost threshold (exactly 15 km, 15.1 km, 0 km)
- `BookingService.cancelBooking`: all five branches of the refund matrix
- `PaymentService.processPayment`: deposit path, full-payment path, double-pay guard
- `InvoiceService`: invoice number format, cancellation notes logic

The `@Transactional` two-save pattern in `InvoiceService` (save to get ID, then set `invoiceNumber`, save again) is also untested. If the second save fails in a non-transactional context the invoice would have a null `invoiceNumber`, which is returned to the client and sent in the email.
