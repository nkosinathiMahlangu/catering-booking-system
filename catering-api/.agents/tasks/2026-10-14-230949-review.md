# Catering Booking System REST API

This is a Spring Boot 3 / JJWT 0.12.x REST API implementing a role-based catering booking system with user registration, package browsing, event booking with transport cost calculation, deposit/full-payment flows, and invoice generation. The implementation follows the plan closely and all four feature branches (foundation, auth, bookings/payments/invoices, package management) are marked completed. The overall structure is sound, but two confirmed bugs need fixing before the API can be used in production: a public endpoint that silently requires authentication, and missing SMTP auth configuration that will prevent all email delivery.

**Watch for:** `GET /api/packages/{id}` is not in the `permitAll()` list — anonymous users hit a 401 trying to view a single package (confirmed). SMTP `mail.smtp.auth=true` is absent from `application.yaml` — Gmail SMTP authentication will fail at runtime (confirmed). The cancellation matrix has an unguarded path when no payment exists and `daysToEvent <= 3`.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The public package listing has a gap: `SecurityConfig` permits `GET /api/packages` (exact path) but not `GET /api/packages/{id}`, which falls through to `anyRequest().authenticated()`. The `CateringPackageController` documents and intends both as public, but the filter chain blocks the single-item lookup.

Booking creation enforces all four business rules correctly. There is one unspecified cancellation edge case — `daysToEvent <= 3` with no payment made — which the code handles with a zero-refund cancel rather than throwing. Whether this should be blocked requires confirmation.

Email delivery is broken by a missing configuration property: `application.yaml` includes `starttls.enable: true` but omits `auth: true`. Gmail SMTP on port 587 requires both. Every OTP and invoice email will fail with a `MailAuthenticationException` at runtime.

`InvoiceController` returns raw `Invoice` entities, which have a `@ManyToOne Booking` → `@ManyToOne User` chain. This will either serialize the full entity graph (including the password hash) or throw a `LazyInitializationException`. Invoice endpoints need a DTO or `@JsonIgnore` on the `booking` back-reference.

<details>
<summary>Issues (5)</summary>

1. **GET /api/packages/{id} blocked for anonymous users** — `SecurityConfig` only permits `GET /api/packages` (exact path); `GET /api/packages/{id}` falls to `anyRequest().authenticated()`, returning 401 for unauthenticated callers. Add `.requestMatchers(HttpMethod.GET, "/api/packages/**").permitAll()` before the ADMIN rules.

2. **Missing `mail.smtp.auth: true` in application.yaml** — Gmail SMTP on port 587 requires `spring.mail.properties.mail.smtp.auth: true`. Without it, every email send (OTP, invoice) will throw an authentication exception. Add the property alongside the existing `starttls.enable: true`.

3. **InvoiceController returns raw entities — likely serialization failure** — `GET /api/invoices/booking/{bookingId}` and `GET /api/invoices/{invoiceId}` return `Invoice` entities directly. `Invoice` has a `@ManyToOne Booking`, `Booking` has a `@ManyToOne User` and `@ManyToOne CateringPackage` — Jackson will attempt to serialize the entire graph, likely hitting infinite recursion or a `LazyInitializationException` for lazy-loaded associations. Add `@JsonIgnoreProperties` on the `booking` field or introduce an `InvoiceResponse` DTO.

4. **Double-save null window on invoiceNumber** — `InvoiceService` saves an `Invoice` with `invoiceNumber=null`, then sets the number and saves again. If any code reads the invoice between these two saves (e.g., concurrent request), it gets a null `invoiceNumber`. Low-risk for a single-instance deployment but worth a comment or a native sequence approach.

5. **Cancellation with no payment and ≤ 3 days** — The spec matrix doesn't define this case, and the code falls through to an `else` branch that cancels the booking with `refund=ZERO` and message "No payment was made." This is reasonable behavior, but there's no `CancellationNotAllowedException` thrown, so the cancellation proceeds silently. Confirm this is intentional, as the spec's "non-refundable" message only applies when payment was actually made.

<summary>Details</summary>

### GET /api/packages/{id} blocked for unauthenticated users

`SecurityConfig` contains exactly one `permitAll()` rule for packages:

```java
.requestMatchers(HttpMethod.GET, "/api/packages").permitAll()
```

This matches only the exact path `/api/packages`. The controller also exposes `GET /api/packages/{id}` as public-facing, and the Javadoc explicitly calls it out as requiring no authentication. But the filter chain has no `permitAll()` rule for this pattern, so it lands on `anyRequest().authenticated()` and returns 401. The fix is to expand the permit rule to `/api/packages/**` or add a second rule before the ADMIN blocks:

```java
.requestMatchers(HttpMethod.GET, "/api/packages", "/api/packages/{id}").permitAll()
// or
.requestMatchers(HttpMethod.GET, "/api/packages/**").permitAll()
```

Note: `/api/packages/**` would also cover `GET /api/packages/admin/all`, so the second option requires keeping the explicit `@PreAuthorize("hasRole('ADMIN')")` on that endpoint (which is already there) and trusting method security over the filter chain for that one path. Either approach works; the per-path rule is safer.

### Missing SMTP authentication in application.yaml

The mail block reads:

```yaml
mail:
  properties:
    mail:
      smtp:
        starttls:
          enable: true
```

Gmail SMTP requires `mail.smtp.auth=true` alongside STARTTLS. The missing property means Spring Mail sends the connection but skips the AUTH command. All calls to `mailSender.send(...)` — OTP delivery and all three invoice types — will fail at runtime with a `MailAuthenticationException`. Add:

```yaml
        smtp:
          auth: true
          starttls:
            enable: true
```

### InvoiceController entity exposure

`InvoiceController` returns `List<Invoice>` and `Invoice` directly. The `Invoice` entity has a `@ManyToOne Booking` relationship; `Booking` has `@ManyToOne User` which includes the hashed password. In a default Spring Boot Jackson configuration with Hibernate, this will either serialize the full object graph (including the password hash) or throw a `LazyInitializationException` for associations loaded outside a transaction. Neither is acceptable in production. The invoice endpoints need an `InvoiceResponse` DTO, or at minimum `@JsonIgnoreProperties({"hibernateLazyInitializer","handler"})` and `@JsonIgnore` on the `booking` back-reference.

### Cancellation refund matrix — unspecified edge case

The spec matrix has four rows, all conditional on some payment having been made. The code adds a fifth branch for `daysToEvent <= 3` with no payment:

```java
} else {
    refund = BigDecimal.ZERO;
    message = "Booking cancelled. No payment was made.";
}
```

This is defensively correct — allowing a zero-cost cancel for an unpaid booking makes sense. But unlike the `daysToEvent > 3 && !depositPaid && !fullyPaid` case (which throws `CancellationNotAllowedException`), this path silently proceeds. If the business intent is that any cancellation within 3 days of an event should be gated regardless of payment state, this else branch should also throw. Confirm with the product owner.
